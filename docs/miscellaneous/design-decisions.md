# Design Decisions

Format: decision → alternatives → reason. Kept up to date as we build.

| # | Decision | Alternatives considered | Reason |
|---|---|---|---|
| D1 | Deterministic eligibility engine decides; the LLM only understands and explains | Let the LLM read policy text and decide | Money-related rules must be exact and testable (e.g. day 29 vs day 31). The LLM cannot overrule the engine; an output guardrail checks consistency. |
| D2 | `uv` with Python 3.12 pinned | pip + venv on installed 3.14 | uv is fast and reproducible (`uv.lock`); 3.12 has wheels for Chroma/RAGAS and matches the Docker base image. |
| D3 | `tasks.ps1` beside the `Makefile` | Install GNU make | make is not native on Windows; the PowerShell script gives the same targets without installing anything. |
| D4 | Tools return `ToolOk`/`ToolError` objects and never raise | Exceptions | The orchestrator can retry or degrade on a typed error code; no crash path. |
| D5 | `customer_id` is a required argument of `lookup_order` and `check_eligibility` | Ownership check in `lookup_order` only (master prompt signature) | `check_eligibility` would otherwise reveal outcomes for orders the customer does not own. |
| D6 | Late delivery counted in **calendar days** (>2 days late) | Business days as originally written in POL-05 | With the fixed data (ORD-1012 is 4 calendar days late on a Monday) only 2 business days have passed, which would contradict the expected "refund shipping fee" result. POL-05 text was edited to match. **To be confirmed by the user.** |
| D7 | *Superseded by D52.* International returns carried no flat deduction (the customer paid real return shipping) | Deduct the flat fee for everyone | The store is now in the Philippines, so there is no international case; the fee depends on where the order is delivered (D52): ₱200 within Metro Manila, ₱500 outside. ORD-1025 (Bulacan) has a maximum of ₱2,350.00. |
| D8 | Optional `item_sku` argument; multi-item order with no item given returns `need_info` | Refund the whole order | ORD-1029: refund only applies to the returned item. |
| D9 | `escalate_to_human` writes `logs/escalations.jsonl` | Database | Mock only, easy to inspect, git-ignored; never contacts anyone. |
| D10 | Fault injection reads the env var on every call | Read once at import | Tests and demos can switch faults on and off without a restart. |
| D11 | Safety hazards (ORD-1023) are escalated directly with `escalate_to_human`, not through the eligibility engine | Add a safety request type | The engine covers the 11 request types in the spec; safety is an "always escalate" trigger decided before any rule runs. |
| D12 | Adopt the course stack (Sessions 3-9): LangChain 0.3 + LangGraph 0.6 + Qdrant + RAGAS 0.4.3 + Guardrails AI 0.11 + Langfuse | Keep the master prompt's framework-light stack (plain Python, Chroma, custom guardrails) | The instructor's notebooks define the technologies the capstone must show. Scope chosen by the user: "core plus light touches". |
| D13 | Vector store is local persistent **Qdrant** (`qdrant_db/`), replacing Chroma | Keep Chroma | Qdrant is used in Sessions 3-6 and 9. Local mode allows one client per folder, so clients are shared per path (`app/rag/ingest.py`). Point ids are UUIDs derived from the readable chunk id. |
| D14 | Baseline chunking uses LangChain `RecursiveCharacterTextSplitter` measured in tokens (800, overlap 100, tiktoken `gpt-4o`) | Own word-window chunker | Same splitter and `tiktoken_len` idea as Sessions 3-5. Falls back to a word estimate if tiktoken cannot download its encoding. |
| D15 | Embedding cache = `CacheBackedEmbeddings` + `LocalFileStore` (SHA-256 keys, namespace = model name, query embeddings cached) | `diskcache` | Course Session 9 technique. Different models never share cache entries (tested). |
| D16 | `override-dependencies` pins `langchain-core` to 0.3.x and `openai` to 1.x | Move to LangChain 1.x | `guardrails-ai 0.11` asks for `langchain-core>=1.0`, but Sessions 4 and 9 stay on 0.3. The same override is used in the Session 9 pyproject. A dependency spike confirmed that every package imports on Python 3.12. |
| D17 | No MCP server or client | Add a FastMCP server for the tools (Session 8) | User decision. Lesson kept: tool results, order notes and retrieved text are untrusted data. Listed in limitations. |
| D18 | Tracing stays **Langfuse** (not LangSmith); semantic cache will be **Qdrant-based** (not RedisVL); no Cohere rerank | LangSmith, Redis, Cohere | User decisions. Retrieval improvements will use section-aware chunking, BM25 + dense ensemble and MultiQuery instead of a reranker. |
| D19 | Orchestrator is a LangGraph `StateGraph` with an injectable LLM object (`parse(system, user, schema)`); structured output via `chat.completions.parse` | Plain-Python state machine; LangChain `ChatOpenAI.with_structured_output` | Course stack (S3, S6) and the OpenAI structured-output lesson (S1). The injectable object keeps tests offline and lets later slots add Langfuse and caching. |
| D20 | The LLM drafts only wording; the app sets `approval_level`, caps `amount` at the engine maximum, keeps only citations present in retrieved chunks, and derives `requires_human_approval` from the recommendation (was "forced true"; superseded by D47) | Trust the LLM output | D1 in code: one repair attempt if the recommendation is not allowed, then a safe escalation (`guardrail_status=fallback`). |
| D21 | Safety, legal, fraud, harassment and "wants a human" flags come from the understanding step and escalate directly before any order tool runs | Add them to the eligibility engine | Extends D11. Urgent only for `safety_hazard`. |
| D22 | The wrapper retries rate-limit, timeout and connection errors twice (1 s, 2 s backoff) and drops `temperature` for models that reject it | Fixed temperature 0 | The user's `.env` model `gpt-5-nano` returns 400 for `temperature=0`. |
| D23 | Human review is a LangGraph `interrupt` in a `review` node, with `MemorySaver` and one thread per case (`CASE-xxxxxxxx`); `resolve()` returns `review_status=pending`, `review()` resumes it | Separate approval table; no gate | Course pattern (S8 Lab 3: approve, edit, deny). Clarifying questions skip the gate. Approve, Edit and Escalate write `logs/audit.jsonl` only (edited text is stored as a character count, not content). Pending cases live in memory, so a restart loses them. |
| D24 | Session memory is in-process: last 6 turns plus a `CaseState`, 30-minute TTL, keyed by session and customer | Redis, database | Master prompt 6.3: no long-term customer data. A follow-up like "It's ORD-1001" keeps the earlier intent. A session id reused by another customer starts fresh. |
| D25 | Every request gets a `request_id` through a context variable; each graph stage logs `latency_ms` | Pass the id by hand | One id ties together all the log lines of a request without changing every call. |
| D26 | Overall request deadline of 30 s through a worker thread; on timeout or unexpected error the answer is a safe escalation | Rely on the per-call OpenAI timeout only | The app stays up. A timed-out thread may finish in the background (its result is discarded). |
| D27 | When order tools are down, the answer is a policy-only escalation with the visible notice "Could not verify the order"; a policy question the documents do not cover (`covered_by_policy=false`) escalates as `policy_gap` | Let the LLM improvise | Master prompt section 8. Implemented without an LLM call so it works even when the LLM misbehaves. |
| D28 | The Gradio UI calls the same `Agent` object as the API (mounted at `/ui`), not the HTTP endpoints | UI calls the API over HTTP | One process, one session store, one set of pending cases. The UI logic is plain functions that tests call directly. |
| D29 | Rate limit (10 per minute per customer) and a global daily request budget are enforced inside `Agent.resolve`, so the API and the UI share them; the API answers `429` + `Retry-After` | Middleware on the API only | The UI calls the agent directly (D28), so a middleware would miss it. |
| D30 | Langfuse: LangGraph callback handler per request (session and user ids are hashed) plus the Langfuse drop-in OpenAI client for tokens and cost; off when keys are missing or `LANGFUSE_ENABLED=false`; tests always turn it off | Trace by hand with `@observe` | Course tool. Tracing must never break a request, so every call is wrapped. |
| D31 | For gpt-5* and o* models the wrapper sends no temperature and `reasoning_effort=minimal` (config `LLM_REASONING_EFFORT`) | Default reasoning effort | Measured on your `.env` model gpt-5-nano: the draft step took 25.7 s at default effort and 2.6 s at minimal, which matters with a 30 s request deadline. |
| D32 | The retriever is warmed up at app start (and in the scenario script) | Load on first request | A cold first search took 16 s (imports, vector store, first embedding call). |
| D33 | `ragas` moved to a uv dependency group `eval`; the Docker image installs `--no-dev --no-group eval`; startup ingests the policies if the store is empty | Ship everything; bake the store into the image | Smaller image and less memory on a free host. Baking the store would need the OpenAI key at build time. |
| D34 | `torch` is a direct dependency pinned to the PyTorch CPU index on Linux only (`[tool.uv.sources]`) | Default torch wheel with CUDA | The Guardrails AI validators (PII, jailbreak, topic) pull in torch. The GPU build added about 3 GB of CUDA libraries and a 10+ minute build; the container has no GPU. Measured image size is 5.66 GB (the earlier "1.87 GB" figure was wrong). Windows keeps the default wheel. |
| D35 | Secret scanning uses **detect-secrets** (pure Python pre-commit hook) instead of gitleaks | gitleaks (master prompt); commit with `--no-verify` | The antivirus flags `gitleaks.exe` and blocks the hook ("Access is denied"). detect-secrets has no executable, still runs on every commit and was shown to block a fake API key and an AWS key. Skipping hooks would have removed the safety net. Deviation from the master prompt and test guide SEC-02 to SEC-04, which name gitleaks; the equivalent evidence is the detect-secrets run plus the history grep. |
| D36 | Safety hazards are also detected by a **keyword net** in code (`SAFETY_WORDS`), on top of the LLM `safety_hazard` flag | LLM flag only | The evaluation showed the flag missing for "power bank is overheating" under all three prompts. Safety (POL-10: always urgent) must not depend on one non-deterministic field. See `docs/debugged-failure.md`. |
| D37 | `error_origin` from the LLM is kept only if the customer's own words say who made a personalisation mistake (`ERROR_CUES`); an order owned by another customer escalates with a generic reply (the ownership part is superseded by D55) | Trust the LLM value; answer `need_info` for ownership mismatch | The engine trusts its inputs, so inputs derived from the LLM are validated in code (extends D1). The test guide expected S23 to escalate. |
| D38 | Default draft prompt is **v2_grounded** | v1 baseline, v3 checklist | Highest task completion (0.971) in the 34-input comparison at about the same cost as v1; v3 costs about 12% more tokens and was not better (`docs/prompt-comparison.md`). |
| D40 | Default retrieval stays **baseline chunking + dense, k=4**; section chunking (`CHUNK_STRATEGY=section`), BM25 hybrid and MultiQuery (`RETRIEVAL_MODE`) are implemented, tested and switchable | Switch the default to the "improved" setting | The 9-configuration RAGAS comparison (`docs/evaluation.md` 1b) showed none beat the baseline on a 10-document corpus: section chunks cut hit rate to 0.85, hybrid cut precision, MultiQuery doubled latency with no recall gain. |
| D41 | Guardrails are layered rules first (regex PII masking, attack and scope rules, output checks), with Guardrails AI validators as an optional second opinion (`GUARDRAILS_AI_ENABLED`, default off) | Guardrails AI as the main layer | In the measured run the validators added nothing the rules missed, tripled latency and blocked a safety report as off-topic. `GuardrailsPII` and `CompetitorCheck` cannot load here (spaCy overflow). `transformers` pinned `<5`. Telemetry disabled. Details in `docs/guardrails.md`. |
| D42 | A citation that is not in the retrieved chunks makes the draft fail once (repair); if it is still wrong the citation is dropped. Rule-consistency and moderation failures after the repair become a safe escalation | Always escalate on a bad citation | A dropped citation cannot mislead anyone; escalating every mis-citation would hand too many cases to humans. |
| D43 | Exact cache sits at the LLM-call level (`CachedLLM`, key = full prompt + model + schema); tools still run every request | Cache the whole response by message text | Order facts and policy text are inside the prompt, so a changed order or policy is a miss automatically and no order-state hash is needed. Cost: paraphrased order cases never hit. |
| D44 | Semantic cache is for general policy questions only, and a hit is an `inform` answer with no human decision (was: parked at the review gate; superseded by D47) | Serve cached answers directly; cache order cases too | Order answers depend on live data and on the customer. The draft stays reviewable. Guarded by key terms because similarity alone cannot separate near neighbours (measured 0.92 for "opened" versus "unopened"). Default threshold stays 0.92 (1 of 5 paraphrases hit); 0.85 would admit 4 of 5. |
| D45 | Guardrails AI turns the OpenTelemetry SDK off only when `HubGuards` is built, not at import | Set it at import (first version) | Langfuse is OpenTelemetry based; the import-time setting disabled tracing for every deployment. Consequence: enabling the optional hub switches Langfuse off. **Superseded by D64.** |
| D46 | Synthetic questions come from the RAGAS pre-chunked pipeline on `## ` section chunks, are stored as unreviewed candidates apart from the golden set, and carry automatic triage flags | `default_transforms` on whole documents; merge candidates straight into the golden set | `default_transforms` crashed on 600-token policies. Generated questions are uneven (8 of 16 flagged), and a model-written reference answer is not ground truth, so nothing counts until the owner reviews it. |
| D47 | A human decision is needed only when policy keeps the case for a person: `requires_human_approval` is true exactly when the recommendation is `escalate`. In-policy `refund`, `refund_partial`, `replacement`, `store_credit`, `cancel_order`, `update_address`, `deny`, `inform` and `need_info` end without a pause (`review_status=not_required`). New POL-10 item 10: an address change on a processing order escalates when the order total is above ₱5,000, a chargeback is open, or the customer has 3+ refunds in 90 days. After shipment a cancel or address change stays an automatic deny (POL-07) | Pause every case (master prompt, D20, D23); pause every money or order-changing recommendation; escalate after-shipment cancel or address change | The capstone spec (section 3) only says decision support and no irreversible action, not "approve everything". The rules engine already turns every high-risk case into `escalate` (above ₱5,000, chargeback, 3 refunds in 90 days, late damage claim, fraud, legal, safety, policy gap), so the rule is one line. No tool executes a refund or order change, so an in-policy refund is still only a recommendation and a reply draft. The prompts v1 to v3 still say a human reviews every answer; they are kept as evaluated, and a corrected variant `prompts/v4_approval_aware.md` was added (not the default until a paid comparison). The working copies of the master prompt and the test guide in `02_Output` were updated to the new rule; the originals in `01_Input` are untouched. Consequence: the saved scenario run (S01 to S24 at 1.00), the refusal run, the RAGAS baseline and the golden set predate this change and POL-10 version 1.1. **Superseded in part by D50 (2026-10-30):** an in-policy `refund`, `refund_partial`, `replacement`, `store_credit` and `cancel_order` is now executed by the agent (mock), so "no tool executes a refund" no longer holds; `requires_human_approval` is still true exactly for `escalate`. |
| D48 | The page has two zones: Customer Chat, and a Developer Debug View (hidden until "Show developer view" is ticked, chat hidden meanwhile). Every escalation message shows in the chat at once; the page has no Approve / Edit / Escalate buttons. Model confidence reads "Not applicable" for any escalation | Keep a reviewer panel with Approve / Save edit / Escalate and a "waiting" chat bubble | Policy, not confidence, decides escalation, so a confidence band would mislead. The customer already sees the escalation message, so a waiting bubble and a draft box duplicated it. `Agent.review` stays in the backend and its tests; only the UI buttons are gone (a spec mismatch, noted here). **D50 adds** a hand-off block under Agent Process for every escalation. **D51 moves** the Developer Debug View to its own page `/ui-dev`; the chat has no developer zone. |
| D50 | The agent **executes** what Brightcart policy lets a support agent approve (refund, partial refund, store credit, replacement, cancellation up to ₱5,000) with a new mock tool `execute_resolution`, and escalates to a person only on a POL-10 rule or a policy gap. Execution = one line in `logs/resolutions.jsonl` plus a change in a runtime overlay `logs/order_state.json` merged into every order and customer read; `data/` is never edited. The tool re-checks ownership and re-runs the rules engine itself, refuses a repeat of the same request, and an escalated case is never executed (including a customer who asks for a human, even when the request is within policy). Every escalation carries a structured hand-off payload (customer id and first name, what was wanted, why, policies, urgency, facts, `executed: false`), shown under Agent Process in the Developer Debug View; the escalation log keeps ids only. `tool_failure` and `low_confidence` stay as a labelled **system fallback**, not a policy reason. An address change is still only answered (the app never handles addresses). The input rule `action_request` is removed (GR-10 is now benign). New prompt `v5_executing` is the default | Keep decision support only (D47); execute into a ledger without changing the order; remove technical escalations | The policies (POL-01, 02, 04, 06, 08, 09, 10) say an agent may approve these resolutions up to ₱5,000, and POL-10 lists exactly when a person decides, so code and docs now match the policies. The overlay makes a second refund of the same order fail the existing rules and makes the three-refunds rule work for real. The capstone specification (section 3) says the agent should be "a decision-support assistant, not an autonomous system that executes real-world transactions. Avoid designs that move money, place real orders, or take irreversible actions." The owner chose to have the agent execute what policy lets a support agent approve. To stay inside the wording, the execution is a mock: a ledger line and a runtime order change, no real payment or order system, reversible by clearing the runtime files, and `data/` is never edited. The risk of a grader reading the spec sentence strictly is accepted by the owner and stated here. Consequence: every evaluation number dated before 2026-10-30 (scenarios, refusal suite, RAGAS, judge, cache benchmark) predates execution and prompt v5; a paid re-run needs the owner's yes. The owner's `.env` must set `PROMPT_VERSION=v5_executing` (or remove the line). |
| D51 | Every customer message becomes a **case** with one `status` (`processing`, `escalated`, `in_review`, `completed`) and `resolved_by` (`chatbot` or `staff`), kept in `logs/cases.json` and shared by **three pages**: customer chat `/ui`, staff review `/ui-staff`, developer debug `/ui-dev` (read-only). The customer page shows the status as a badge and picks up the staff reply by a 5 s timer or a Refresh button. Staff open an escalated case, read the hand-off packet and decide: **approve** (carries out the chatbot's suggested action), **modify** (action and amount chosen by staff) or **reject** (nothing executed). Approve and modify execute the mock with staff authority (`execute_resolution(..., staff_authorized=True)`), still idempotent and capped at what is left to refund on the order. The developer view left the customer chat, so the `?debug=1` gate is retired. The staff page has **no login** | The flow in `01_Input/resolveright_processing_flow.md` has `data/cases.json` and a demo login `staff / demo123`; record the staff decision only; escalate on low confidence | The flow document asks for a visible "completed" state for both paths and a place where a person finishes an escalated case. The case file lives in `logs/` (git-ignored runtime data), not `data/`, so `data/` stays read-only (D50) and customer text can never be committed. Staff execution is the same mock as D50, so a staff-approved refund shows up in the ledger and in the order overlay. `low_confidence` stays a labelled system fallback (D50), not a policy reason. A hard-coded password in the repo would break the secrets rule, so the owner chose no login for the demo: anyone with the `/ui-staff` address can act as staff. This is a limitation, listed in `docs/limitations.md` ("Limitations and next steps"); production needs real staff authentication. Consequence: one JSON file and one lock, so ONE server process only (same limit as Qdrant); on Render the file is wiped on every deploy. The API `POST /api/v1/review` accepts `approve`, `modify`, `reject` (plus the older `edit` and `escalate`) and `GET /api/v1/cases/{id}` returns the status. |
| D52 | **The store is localized to the Philippines.** Money is in pesos (₱): agent approval limit ₱5,000 (was $150); return-shipping fee ₱200 for orders delivered within Metro Manila and ₱500 outside it (was a flat $6.95); free standard shipping over ₱1,650, flat fee ₱200 otherwise. Every other seed price was rescaled (about x33, rounded to ₱50, same ordering as before: for example a laptop ₱30,000, a chair ₱10,650 above the limit, a speaker ₱4,350 below it). The international order case (Canada) is removed; ORD-1025 is now delivered to Bulacan and pays the higher fee. Orders carry `shipping_region` instead of `shipping_country`; customers are `PH`; the reason code `INTERNATIONAL_RETURN` became `OUTSIDE_METRO_MANILA_FEE`. PII masking also covers Philippine mobile and landline numbers, SSS and TIN numbers and barangay address lines. Amount checks accept ₱, `PHP` and a stray `$`. Dollar amounts in earlier rows were converted; API costs stay in **USD**. | Keep the numbers and swap only the symbol; keep Canada as the foreign case; convert at a live exchange rate | The owner chose realistic peso values and a Metro Manila / provincial fee over a symbol swap, and removed the international case. A fixed table keeps tests and policies reproducible (a live rate would change expected values). The amounts in the stored evaluation results (`docs/evidence/evals/`) and in the earlier write-ups predate D52 and are not rewritten; they must be re-run after the owner's golden-set review (paid, needs the owner's go-ahead). The semantic cache and Qdrant index hold the old policy text until they are re-ingested. |
| D53 | **The case file is deleted every time the server starts** (`cases.reset_store()` in the API lifespan; switch `RESET_CASES_ON_STARTUP`, default on). Only `logs/cases.json` (and a temp leftover) is removed; the order overlay and the resolution ledger stay. Written down as a limitation in `docs/limitations.md` (Case store). | Keep cases and show only today's; a "Clear" button on the staff page; purge cases older than a time limit | The staff page has no login and the file holds customers' conversation text and hand-off packets, so cases from an earlier session are stale and should not outlive it. A wipe at start-up is the simplest rule for a demo; the cost (a waiting case is lost on restart) is accepted. A database with a retention rule is the next step. |
| D49 | Customers see only the green header, Customer Chat, message box and Send. The "Developer view (for testing only)" block with the "Show developer view" checkbox appears only when the page is opened with `?debug=1`. The Demo setup accordion ("Demo setup to fill in message to be sent above(for testing only)", under Send) is always shown (owner decision). Green theme and CSS follow `01_Input/resolveright_gui_style.md`, passed to `gr.mount_gradio_app` | Always show the demo tools; real login to protect them | The checkbox looked like a chat option and the debug tools are not for real customers. The URL parameter is a convenience gate, not security: anyone can add it, so it must not guard anything sensitive (the page holds no secrets, and the API is unchanged). Gradio 6 takes `theme` and `css` on mount, not on `Blocks`. The amber escalation note and sample chips of the style guide were not added. **Superseded in part by D51:** the developer view and the `?debug=1` gate are gone from the customer page (the developer page is `/ui-dev`); the Demo setup stays under Send and now holds links to `/ui-staff/` and `/ui-dev/`, under a dotted divider (`.test-section`). |
| D39 | The RAGAS judge is `gpt-4o-mini` (`JUDGE_MODEL`), a different model from the agent's `gpt-5-nano`; evaluation results are saved with versions and settings, and evaluation code lives in `eval/` | Same model for agent and judge | A model grading its own output is biased; `gpt-5-nano` with reasoning also fails on some RAGAS prompts (n>1, temperature). Known cost: the judge returns one generation instead of three for `answer_relevancy`, which makes that metric noisy. |
| D54 | **Start-up ingest runs every time, not only on an empty index** (ensure_policies_ingested in app/api/main.py). Unchanged policy files are skipped by their content hash (no OpenAI call); changed files are re-embedded. A failure is caught, logged as `startup_ingest_failed` and the app starts on the existing index | Keep ingest on an empty index only (D33); a `make ingest` reminder; a file watcher | After D52 rewrote the policies, the unchanged-but-stale index kept returning the old $6.95 fee to a customer. An index that silently lags the policy files is worse than a few cents at start-up. |
| D55 | **Someone else's order looks like a missing order** (tool layer, `check_order_access` in `app/tools/orders.py`): an owner mismatch returns the same `not_found` error as an unknown id (the `ownership_mismatch` code is gone), the agent answers `need_info` with a neutral reply ("I couldn't find that order on your account. Please check the order number, or I can help with one of your other orders."), and the case is `completed` / `chatbot`: nothing reaches Staff Review. A server log line `order_access_denied` (no ids) keeps an audit trail | Escalate to staff (D37); a different message for a mismatch | The reply and the trace cannot tell a customer whether an order id exists or whose it is; staff no longer get a case with nothing to approve. | D56 | **All three pages open in dark mode** (`FORCE_DARK_JS` passed as `js` to every `mount_gradio_app` in `app/server.py`); the message box left of Send gets an explicit light text colour, caret and placeholder | Follow the browser or OS setting (the old behaviour, so the pages looked light); a dark-only theme object | One switch covers customer, staff and developer pages, and the dark CSS rules that already existed now apply. | D57 | **Two customers, and no customer picker on the chat page.** The data has Nora (C-001, the fixed demo user, `config.DEMO_CUSTOMER_ID`) and Milo (C-002, data only). Nora owns 14 orders: every one behind an MVP scenario or a demo sample (refund, window and final-sale declines, over-limit and safety escalations, replacement, missing parcel, cancel, personalised, opened consumable, gift card). Milo owns the other 16, so Nora asking about one of them tests the ownership guardrail (D55). All 30 orders stay. The processing flow's Scenario 5 (customer changes mid-chat) cannot happen, so it is not built. The API, tools and session memory still take any `customer_id`. The 3-refunds-in-90-days rule is per customer, so neither seed customer has it (it would escalate every refund of that customer); S17 was dropped (24 to 23 tool scenarios, the spec needs 15) and the rule is unit-tested with a patched customer | Keep 18 customers; Nora gets all orders (no ownership test); give Milo 3 refunds | The owner asked for one real customer plus data-only owners. Old saved eval results and judge sheets keep the old customer ids and stay as the record of those runs; re-running them is the owner's call (paid) |
| D58 | **Messages while a case waits for staff are routed by rules, not by an LLM** (`app/followup.py`, called first by `cases.handle_message`). Open = `escalated` or `in_review`. A message that names the held order or CASE id, or is about the held matter, is a status check, new information or a repeat: it gets a fixed reply and the agent is not run, so the chatbot can never decide, promise or change a held case. Only new information changes the case (appended, masked, `has_new_customer_message`); status, repeat and unclear replies leave it byte-identical. Anything else (policy question, another order) runs the normal pipeline in its own case; a short pronoun question ("How long does it take?") gets one clarifying question. Messages with a safety word or that the input guardrails would not allow never take the shortcut. Staff see a 💬 New msg marker and a Reload case button that does not touch the form. The customer page keeps a list of cases, shows one badge per open or recent case, and delivers each staff reply as "Update on CASE-...", after the current answer (also when it arrived just before the send).
