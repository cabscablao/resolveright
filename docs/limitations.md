# Limitations and next steps

Stated plainly, so a reader knows what the results do and do not show.

## Limitations

| Area | Limitation |
|---|---|
| Data | All data is synthetic: 10 policy documents, 2 customers (Nora, who is the fixed demo user, and Milo, who only owns orders so the ownership guardrail can be tested), 30 orders. No real store, person or payment is involved. Orders are mock records read from JSON. |
| Execution | "Execution" is a mock (D50): a line in `logs/resolutions.jsonl` and a change in a runtime copy of the order. There is no payment or order system, `data/` is never edited, and the runtime files are wiped with the disk on Render. An address change is only answered (the app never handles addresses). The capstone spec asks for a decision-support assistant and says to avoid designs that move money; the owner chose mock execution knowingly (D50). |
| Staff authentication | The staff page `/ui-staff` has **no login** (D51): anyone who knows the address can open escalated cases and decide them, which can execute a (mock) resolution. This is a demo choice by the owner; a hard-coded password in the repo would break the secrets rule. Next step: real staff authentication (single sign-on, or at least a password from the environment) and an audit of who decided. The developer page `/ui-dev` is also open and shows first names and case text (masked). |
| Regional rules | The only regional rule is the return-shipping fee: ₱200 within Metro Manila and ₱500 outside it (D52). There are no per-province shipping rates, no courier integration, no Philippine tax or holiday calendar (the policies only say Philippine public holidays), and amounts are fixed pesos with no currency conversion. The PII masking covers common Philippine phone, SSS, TIN and barangay formats, not every id or address style. |
| Case store | Cases live in one JSON file (`logs/cases.json`) with a lock, so it works for ONE server process only. The file is deleted every time the server starts (`RESET_CASES_ON_STARTUP`, default on, D53), so the Staff Review page never shows cases from an earlier session. The consequence is that escalated cases do not survive a restart or a Render deploy: a case still waiting for staff disappears, the customer page then shows no status for that case id, and there is no history or audit of past cases (the order overlay and resolution ledger are kept). It is not a ticketing system: no assignment, SLA timer, notification (Slack or email) or live takeover. The pages poll every 5 seconds instead of receiving pushes. Next step: a database with a retention rule instead of a wipe, and a real helpdesk. |
| Follow-ups on a held case | The router that decides whether a message is about a case waiting for staff (D58) is a set of word lists (`app/followup.py`), not a language model. Paraphrases it misses count as unrelated or unclear, which is safe (the case is never changed or decided), but the customer may get a general answer or a clarifying question instead of a status reply. Withdraw (`status=withdrawn`) and urgent (`priority=high`) follow-ups of the processing flow (5.2, rows 4 and 5) are not built: "cancel my return request" and "let me talk to someone" go through the normal pipeline. Staff are "notified" only by the New msg marker in the list; there is no email or Slack. |
| Customers | The customer page has no customer picker and always chats as C-001 (D57); the API still takes any `customer_id`, and a real product would take it from a login. Because the 3-refunds-in-90-days rule is a per-customer count, no seed customer has it: it is unit-tested with a patched customer. |
| Refund history | Order state (`logs/order_state.json`) and the resolution ledger (`logs/resolutions.jsonl`) are deleted at every server start (D60), so there is no refund history across restarts: an order refunded in one session can be refunded again after a restart. A real product would keep them in a database. Set `RESET_CASES_ON_STARTUP=false` to keep them (and the cases) while debugging. |
| Scope | The rule engine covers 11 request types (return, damaged, defective, wrong item, late, lost, cancel, change address, warranty, price adjustment, refund status). Anything else is answered from the policies or escalated. |
| Language | English only. Guardrail rules are English patterns. |
| Corpus size | Ten policies of about 600 tokens each. Retrieval scores are near perfect, and section chunking, hybrid search and MultiQuery could not beat the plain baseline here (`docs/evaluation.md` 1b). On a larger corpus the result may differ. |
| Evaluation | Small sets (25 golden questions, 23 scenarios (24 before D57), 26 guardrail cases), one run per configuration. The sets were written by the same author as the system. The tool scores (1.00) are **after** the fixes in `docs/debugged-failure.md`, not a first-try result. |
| Human review | The synthetic candidates were reviewed on 2026-11-02 (5 dropped, 10 edited, 1 kept) but the review was AI-assisted (confirmed by the owner), so it is not an independent human review. The golden set is marked reviewed, but the reviewer was an AI assistant (Claude) at the owner's request, not an independent human (`docs/evaluation.md` section 4). The judge "hand scores" (JD-03) were produced with LLM assistance, not by an independent human (disclosed in `docs/judge-agreement.md`), so the agreement figures compare two models, not a model and a person. The reference answers were drafted by the assistant, so drafting and review are both by an AI. |
| Judge | The LLM judge is lenient and does not see the order record, so it cannot catch a wrong fact that comes from order data. |
| Guardrails | Pattern based. Paraphrases, other languages, ROT13 or hex text and multi-turn attacks can get through. GR-18 (an "already approved" claim for a refund over ₱5,000) is not escalated. Details in `docs/guardrails.md`. |
| Semantic cache | Serves only general policy questions, and at the safe 0.92 threshold only 1 of 5 paraphrases hit. Order-specific requests use the exact cache only. Indicative numbers from one run (`docs/caching.md`). |
| Deployment | Render free plan: the instance sleeps when idle (the first request can take about a minute), the disk is wiped on every deploy, and sessions and pending review cases live in memory and are lost. One worker only, because local Qdrant allows one process per folder. |
| Guardrails AI | On by default in the code since D64 (2026-11-02) but off on the Render free plan (512 MB of RAM is too little for its models). It is slow (9 s per case against 2.7 s, measured before it became the default) and needs model downloads. It no longer switches Langfuse tracing off. `GuardrailsPII` and `CompetitorCheck` do not load in this environment. |
| Cost control | A per-minute limit and a daily request budget protect the bill, but they are per process and reset when the instance restarts. Set a spend limit in the OpenAI dashboard as well. |

## Next steps

1. Fix GR-18 with an intent rule for "refund" plus an amount over ₱5,000.
2. Done 2026-11-02: the reviewed synthetic candidates are merged into `eval/golden_rag_sdg.jsonl` and the RAGAS baseline was re-run on the larger set (`docs/evaluation.md` 1b). That run found one citation to a chunk that was not retrieved (SDG03); a rule added to `prompts/rag_answer.md` removed it in the next run (0 of 36). RAGAS faithfulness on short answers varies with the judge (G10 scored 0.5 in 2 of 5 re-scores for an answer that matches the policy word for word).
3. Test retrieval options again on a larger policy corpus.
4. Add a persistent store (database) for audit entries, sessions and the cache, so a restart loses nothing.
5. Add guardrail rules for more languages and multi-turn attacks, and measure them on a larger attack set.
6. Split `app/agent/graph.py` (about 1,200 lines) into smaller modules.
